# Механизм офлайн-режима и синхронизации данных

## Проблема

В AS-IS при обрыве интернета магазин теряет карты лояльности (INC-8402), а при отказе локального сервера — полностью останавливается (INC-8433). В TO-BE касса должна работать при временном отсутствии связи.

## Офлайн-режим Cloud POS (PWA)

Cloud POS — PWA на планшете. При потере соединения приложение переходит в Offline Mode (Service Worker + IndexedDB).

- **Наличные чеки.** Чек пишется в Outbox Queue (IndexedDB). Фискализация — через HAL-драйвер локально, печать чека не зависит от интернета.
- **Карты.** HAL передаёт команду `pay()` в терминал. Авторизация идёт по каналу самого терминала (GPRS/Ethernet), а не по интернету планшета. Если терминал не может авторизоваться — кассир переходит на наличные (ограничение эквайера, не архитектуры POS).
- **Лояльность.** В IndexedDB кэшируются балансы и правила начисления (активные промо, множители, сегменты). Списание идёт по кэшированным правилам; при отсутствии правила — базовое начисление 1 балл/рубль, чек помечается `loyalty_pending=true`.
- **Цены.** Проверяются по каталогу из IndexedDB (синк по расписанию 15–30 мин + по событию изменения каталога).

### Cold start и TTL

Каталог, промо и балансы лояльности предзагружаются при каждом успешном синке и хранятся со snapshot + TTL. При холодном старте без интернета PWA использует последний snapshot. Если snapshot старше N часов — касса работает «по последней известной цене» с флагом `stale_price=true` для последующей сверки в Sync Service. Продажа не блокируется.

## Синхронизация при восстановлении связи

1. **Outbox Queue → POS Backend** через API Gateway. Каждый чек имеет `client_txn_id` (UUID с планшета) — гарантия отсутствия дубликатов при повторных отправках.
2. **Идемпотентность.** Sync Service проверяет `client_txn_id`; повторные чеки пропускаются. Конфликты каталога — `last-write-wins` по версии.
3. **Loyalty Retro-calculation.** Loyalty Service пересчитывает баллы идемпотентно (key = `client_txn_id`). Если баланс ушёл в минус из-за кросс-канального списания — операция помечается `reconciliation_required` и уходит в ручную сверку; касса не блокируется.
4. **Кэш-инвалидация.** После синка IndexedDB инвалидируется, свежий каталог/промо/правила загружаются из Redis/CDN.
5. **Связь с Task 2.** Чеки с `stale_price`/`loyalty_pending` попадают в отчёт Post-open Monitor и учитываются при проверке порога 2% ошибок ШК.

## Надёжность

- **Retry:** exponential backoff с jitter (иначе 500 магазинов синхронизируются синхронно и положат API Gateway — thundering herd).
- **Приоритет:** сначала чеки (финансовая отчётность), затем лояльность.
- **Мониторинг:** Edge Agent шлёт heartbeat в API Gateway. При офлайне > 30 мин — alert в Prometheus/Grafana → Ops on-call; runbook: звонок в магазин, проверка резервного канала (4G/LTE fallback), эскалация.

## Абстракция над железом: два уровня

Абстракция реализована на двух уровнях с разными контрактами.

### HAL (в магазине, Edge Agent)

Изолирует физическое железо: USB/COM/SDK фискальных регистраторов (АТОЛ, Штрих-М) и терминалов (Сбер ARCUS-2, Ingenico, Verifone, Альфа). Контракт: `pay() / printReceipt() / openDrawer() / scan()`. Новый терминал = новый драйвер в Driver Registry; кассовый софт не меняется. INC-8415 (ARCUS-2): дни, не 3 недели.

### Payment Gateway (в облаке)

Изолирует финансовые протоколы эквайеров. Контракт: `authorize / capture / refund / void`. Router + Tokenizer + сменные Connectors под каждого эквайера. Смена банка = конфиг, не код POS Backend.

Это разные слои: HAL работает при офлайне локально, PG — только онлайн. Кассовый софт (PWA) и POS Backend зависят только от стабильных контрактов HAL API и PG API соответственно.
